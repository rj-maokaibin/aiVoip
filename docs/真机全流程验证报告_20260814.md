## 真机 CALL 级 E2E：非空 findings 验证（2026-08-14，新隧道 47.104.155.247:63314）

> 目标：确认真机通话的 CALL_QUICK 产生**非空 findings**（此前因媒体捕获窗口为空导致
> findings=[]）。**9/9 PASS**（`tools/dev_real_call_e2e.py`）。

### 根因：媒体捕获只覆盖拨号窗口
初版 `build_live_probe` 仅在 `bind_call`（摘机后媒体镜像流激活时）抓一次 **2s** 窗口，

### 修复：通话期间周期性累积 PCM 段
- `RealReproductionPlatform._live_pcap_cache`：`bytes` → **`list[bytes]`**（多段累积）；
- `build_live_probe`：改为**追加**一段 2s 捕获（唯一文件名带时间戳，避免覆盖）；
- 新增 `_merge_pcap_segments()`：合并多个经典 pcap（保留首个 24B 全局头，去重后续段头）；

- `_watch_real` + `dev_real_call_e2e.py`：通话中每 4s 追加一次 `build_live_probe`，
  覆盖整个通话主体（不再是 bind 时的单点窗口）；

## 复现完成 → 自动触发诊断（2026-08-14，闭环断点①修复）

> 补齐"复现会话完成 → 自动触发诊断"的断点。此前复现流程（飞书 provision 自动建
> case + 启动复现 → 真机 CALL 捕获 → CALL_QUICK 非空 findings）跑完后，**诊断必须
> 人工点击** `POST /cases/{id}/diagnosis/start` 才会启动；"飞书一条消息 → 全自动
> 复现 → 全自动诊断结论"的闭环在诊断入口处断掉。

### 实现
- `reproduction_tasks.ensure_reproduction_diagnosis(session_id)`：幂等触发函数
  - 会话达到终态（`COMPLETED` / `PARTIAL_SUCCESS` / `CANCELLED`）且 `cleanup_status ==
    CLEANUP_VERIFIED` 时创建 `DiagnosisRun` + `Job`，并投递 `run_diagnosis` 到
    `diagnosis` 队列；
  - 幂等：该 case 已有 `created_at >= session.started_at` 的诊断 run 时返回
    `ALREADY_DIAGNOSED`（不重复），同时允许新会话新证据触发新诊断；
  - 永不抛异常（不得拖垮复现主流程）。
- 三个触发点：
  1. `watch_fxs_events` 任务完成后（**主要路径**：真机 FXS 事件 → CALL 捕获 → cleanup 结束）；
  2. `cancel_reproduction` 后（取消时可能已有被分析的 CALL 证据）；
  3. `reconcile_reproduction` 兜底扫描（watchdog 恢复 / cleanup 重试通过后，对全部
     终态+cleanup 已验证会话统一触发）。
- `start_reproduction` 返回时也调用一次（覆盖 ARM_FAILED→立即 cleanup 的终态路径）。

- **真实 DB 集成验证**：构造 COMPLETED + CLEANUP_VERIFIED 会话（含 ANALYZED CALL）→

## 诊断 DIAGNOSED → 自动报告 + 自动推回飞书（2026-08-14，断点②③修复）

> 补齐诊断完成后的两个人工环节：**DIAGNOSED 后自动生成诊断报告**、**自动把结论
> 卡片推回飞书**。此前二者都只能靠人工 API（`POST .../reports/diagnosis` /
> `POST .../feishu/sync`）触发；现在诊断一完成即自动发布。

### 实现
- `diagnosis_tasks._publish_diagnosed_artifacts(db, *, case_id, run_id)`（best-effort）：
  1. **生成报告**：调用 `generate_report`（HTML+JSON 落 MinIO，写 DiagnosisReport +
     Artifact），并记 `DIAGNOSIS_REPORT_GENERATED` 审计；
  2. **推送飞书卡片**：仅当 `feishu_live_enabled=True` 时调用
     `FeishuCaseCardService.sync_case_card`（有 binding 则 update 同一卡片，否则
     send 新卡片并持久化 binding）；未启用时返回 `SKIPPED:FEISHU_LIVE_DISABLED`。

## 卡片回传交互 toast 反馈（2026-08-14）

> 支持飞书卡片按钮回传交互两种回调：**`card.action.trigger`（v2 新版）** 与
> **`card.action.trigger_v1`（旧版）**。用户点击卡片按钮（查看详情 / 停止自动复现 /
> 已完成操作）时，回调**立即返回 toast** 反馈点击行为，并在动作改变状态后刷新卡片。

### 实现
- `events.dispatch_event` 识别 `CARD_ACTION_EVENT_TYPES = {card.action.trigger,
  card.action.trigger_v1}`；新增 `_card_action_response()` 为每个动作生成用户可见
  toast（成功/进行中/失败），STOP_REPRODUCTION / EXTERNAL_ACTION_COMPLETED 动作标记
  `updated_card=True`（由异步诊断/清理 worker 推送下一次 `sync_case_card` 刷新）。
- `feishu_callback` 对卡片回传交互事件返回 `{"code":0,"msg":"ok","toast":{...}}`
  （v2 与 v1 结构均兼容：action 在 `event.action.value` 或顶层 `action.value`）。
- 长连接监听器走同一 `dispatch_event`，点击反馈行为与 HTTP 回调完全一致。

  STOP 返回 toast 且投递 cancel、动作失败返回 error toast、HTTP 回调透出 toast。
- 全量回归：**257 passed**（新增 4 项 + 适配飞书已配置的 2 项断言修正；11 个
  F1/F2/F3 环境失败为既有基线，无新增回归）。

> 注：飞书卡片回传交互需要机器人在目标群中（发卡片）以及应用具备 `im:message` /
