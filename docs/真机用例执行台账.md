## KNOWN-DEFECT：通话中 DTMF 未归属到 Call / Attempt

发现于 2026-08-16 执行 RP-D08，session `08ec02b4-1ad6-47df-bedc-e2a658d5268f`。

**现象**：10 个 `FXS_DTMF` 事件全部采集成功（拨号 `3,0,1` + 通话中 `1,2,3,#,7,8,9`，
数字与顺序均正确），但**每一条的 `call_id` 与 `attempt_id` 都是 NULL**。同一 Session 的
`FXS_OFFHOOK`/`FXS_ONHOOK` 则带有 `attempt_id`。

**观测到的时序**：

| 时刻(UTC) | 事件 |
|---|---|
| 07:29:12 | `FXS_OFFHOOK` → attempt no=1 `ACTIVITY_DETECTED` |
| 07:29:14 | DTMF `3,0,1`（拨号） |
| 07:29:21–23 | DTMF `1,2,3,#,7,8,9`（**通话中按键**） |
| 07:29:26 | `SIP_INVITE` → `CALL_BOUND`（Call 此时才存在） |

**根因**（`backend/app/reproduction/orchestrator.py` `record_fxs_event`）：

1. DTMF 分支构造 `ReproductionEventRecord` 时未传 `attempt_id`，也未传 `call_id`，
   因此事件只挂在 Session 上，既不属于 Attempt 也不属于 Call。
2. Call 绑定依赖 PCAP Signal Observer 解析下载回来的抓包，天然滞后数秒；物理上已接通、
   用户已在按键时，系统里 Call 尚不存在，所以写入时刻无 `call_id` 可绑。
3. DTMF 分支以 `if state != ACTIVITY_DETECTED: return None` 开头，意味着一旦绑定完成
   进入 `CAPTURING`，**通话中的 DTMF 会被直接丢弃、连事件都不记录**。本次能留下记录，
   仅因为绑定滞后使按键恰好都落在 `ACTIVITY_DETECTED` 窗口内。

**影响**：任何"通话内 DTMF"的查询恒为空，这也是全库 in-call DTMF 计数长期为 0 的原因；
RP-D08、RP-H08 无法通过。诊断侧目前只能依赖 PCM 的 `DTMF_PATH`，拿不到按键归属。

**修复方向**（尚未实施，需求证）：DTMF 事件写入时绑定当前 ACTIVE Attempt；Call 绑定成功后
回填同一 Attempt 时间窗内已记录的 DTMF 的 `call_id`；并允许 `CAPTURING` 状态继续记录 DTMF
而非丢弃。

`tools/dev_case_ledger.py` 从复现 DB 重算本台账的状态，避免手工对账：


设计约束：DB 不记录操作意图（"说话5秒静音5秒"与"通话30秒"在 schema 中无法区分），
因此工具**不做启发式猜测**：

- Session 只通过显式标注（`docs/真机用例执行台账.labels.json`）绑定到 RP 用例；
  已标注的 Session 按该用例的声明判据自动判定。
- 未标注 Session 仍贡献**跨切面事实**（已采集过哪些 DTMF 数字、是否存在 in-call DTMF
  事件、残留 ACTIVE 行数、锁状态）——这些是矩阵级缺口，不是单例结论。
- 既无标注又无跨切面证据的用例保持 `NOT_RUN`，工具不会凭旁证把用例升级为 PASS。
- `PASS*`（`PASS_NEEDS_NOTE`）表示自动判据全过，但该用例编码了 schema 无法确认的
  操作意图，接受前须补操作者说明。

无论用例声明了什么，安全维度（cleanup=VERIFIED、`mock_platform=false`、
Manifest+checksum、无残留 ACTIVE attempt）对所有已标注 Session 一律强制。
