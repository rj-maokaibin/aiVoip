## 补充记录 3：媒体流"提前结束"实为 CALL_PCAP 窗口截断 —— 根因修正 + 修复（2026-08-16 下午）

### 错误推断修正

早前记录曾断言「RTP 媒体流在挂机前 ~1.5s 提前结束」。**该结论是错误的**。真机会话 `f43f6b7d` 用 tcpdump 核对 pcap 实际包时间发现：

| 事件 | 本地时间 | 相对 |
|---|---|---|
| RTP 流开始 | 19:50:46.033 | 0s |
| INVITE（拨 301）| 19:50:51.692 | +5.66s |
| 200 OK / ACK（接通）| 19:50:52.369 | +6.34s |
| **RTP 流最后一个包** | **19:50:57.563** | **+11.53s** |
| **BYE（挂机）** | **19:50:57.572** | **+11.54s** |

**媒体流实际持续到 BYE 前 9ms，从未提前停止**。此前「提前 ~1.5s 结束」的结论来自 `pcm_rx` 的 `end_abs`（那是 **pcm_analyze 分析窗口结束时间**，不是 RTP 媒体流结束时间）。

### 真正的根因：CALL_PCAP 窗口截断（`build_call_capture`）

- 完整 SESSION_PCAP 直接跑 pcm_analyze → 检出 `301` + **`1234567890`（10/10）** ?
- CALL_QUICK 用的 CALL_PCAP（`calls/<call_id>/call.pcap`）只到 55.753s（973 包），缺 seg5 的 181 包 → 只检出 `123456789`（9/10）?
- 逐段分析：seg4(41444-50410) 含 `123456789`，**seg5(50454-52992) 含 `0`**（绑定本 call、retained）

**根因**：`build_call_capture` 窗口上界 = `FXS_ONHOOK + post_capture(3s)` = 44600+3000=**47600**，而媒体尾段 seg5.start_ms=**50454 > 47600** 被 `_overlap_segments(33047,47600)` 排除——尽管 seg5 明确绑定本 call 且已 retained。固定 post_capture 窗口不够，因为媒体流持续到 BYE 而非 FXS on-hook。

### 修复（2026-08-16 已部署）

`backend/app/reproduction/capture_pipeline.py` `build_call_capture()`：窗口上界在 post_capture 基础上**再扩展覆盖所有绑定本 call 的 retained 段的最大 end_ms**（`call_bound_end`），仍受下一 attempt 起点与最后 retained 段 end 约束（不串入下通呼叫）。

- 单测新增 `test_build_call_capture_includes_call_bound_tail_beyond_post_capture`（call-bound 段起始超过 ONHOOK+post_capture 也须合并）；既有 3 个窗口测试 + 全量 68 单测全部 PASS
- 部署到 3 个 repro worker
