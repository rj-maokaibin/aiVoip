# PON 84B 小包转发速率 1260 Mbps 问题最终定性报告

- 问题单：BUG 1628980
- 产品：RG-PON3000G
- 版本：ReyeeOS 2.412.0.1714
- 测试场景：PPPoE 模式，双 LAN → PON 上行，Renix RFC2544 吞吐量测试
- 报告日期：2026-08-25
- 最终建议：未解评审 Give Up；按“测试统计口径误判、现有证据不支持产品超规格”处理

## 1. 最终结论

经过对信而泰官方 RFC2544 资料、ITU-T/IETF 标准资料以及本次 Renix 原始测试数据进行交叉验证，可以明确确认：

> Renix 报告中的“转发速率（Mbps）= 1260”属于 Ethernet L1 线路速率口径，即在 Ethernet Frame 长度之外，还计入 Preamble/SFD 和 IFG 的线路占用；它不是 Ethernet L2 数据速率，也不能直接等同于 GPON PON/GEM 侧 1.24416 Gbit/s 的上行 nominal bit rate。

84 Byte、63% 这一行的原始测试数据为：

- 转发速率：1,514,422 fps
- 转发速率：1260 Mbps
- 转发数据速率：1017.692 Mbps
- 发包数 = 收包数
- 丢包数 = 0
- 结果：Passed

通过数据反算：

```text
L1 Rate = 1,514,422 × (84 + 20) × 8
        = 1,259,999,104 bit/s
        ≈ 1260 Mbps
```

```text
L2 Rate = 1,514,422 × 84 × 8
        = 1,017,691,584 bit/s
        ≈ 1017.692 Mbps
```

计算结果分别与 Renix 报告的“转发速率（Mbps）=1260”和“转发数据速率（Mbps）=1017.692”完全一致。

因此，1260 Mbps 的来源已经可以由 Ethernet L1 统计公式完整解释。现有证据不存在“ONU 将 1260 Mbps 的有效 Ethernet L2 数据送入 1.24416 Gbit/s GPON 上行”的证明。

原问题将 Ethernet L1 Rate 1260 Mbps 与 GPON 上行 nominal bit rate 1244.16 Mbit/s 直接比较，属于跨层、不同统计口径之间的比较，由此得出“PON 口超过规格”的结论不成立。

### 最终定性

现有测试结果不能证明产品存在 PON 上行超规格问题。

本问题建议在未解评审中 Give Up。Give Up 的含义不是证明所有 PON 内部带宽细节均已完全测量，而是原 BUG 的核心判据已被测试数据反证，当前缺少继续以产品缺陷方向投入研发定位的依据。

## 2. 问题背景

原 BUG 描述为：PPPoE 模式下进行 RFC2544 LAN→WAN 上行测试，84 Byte 小包场景中，转发速率达到 1260 Mbps，高于预期约 1230 Mbps，并被认为超过 GPON 上行 1244 Mbps 规格。

讨论过程中存在两种判断：

1. 异常观点：GPON 上行只有 1244 Mbps，因此 1260 Mbps 必然异常，可能是软件统计、限速或转发逻辑问题；
2. 统计口径观点：需要先明确 Renix 报告的 1260 Mbps 是 L1、L2 还是 PON/GEM 速率，否则不能直接与 GPON 1.24416 Gbit/s 比较。

最终补充的 Renix 原始测试报告，使第二种判断得到直接数据证明。

## 5. 证据三：信而泰官方资料

### 5.1 信而泰官方 RFC2544 吞吐量测试资料

官方资料：

https://www.xinertel.com/newsinfo/165665.html

信而泰官方资料给出了 Ethernet 最大帧率的典型计算：

- 测试帧长：64 Byte
- Preamble：7 Byte
- SFD：1 Byte
- IFG：12 Byte
- 线路实际占用：64 + 7 + 1 + 12 = 84 Byte
- 1 GbE 最大帧率：1,000,000,000 / (84 × 8) = 1,488,095 fps

该官方计算明确证明：信而泰在 Ethernet 最大传输速率/负载计算中，会把 Preamble、SFD、IFG 计入线路占用。

这与本次 Renix“转发速率（Mbps）”字段通过 FPS 反算得到的统计方式完全一致。

## 6. 证据四：IETF RFC 1242 / RFC 2544

### RFC 1242

https://www.rfc-editor.org/rfc/rfc1242.html

RFC 1242 对 Data Link Frame Size 的定义从 Preamble 之后的第一个 octet 开始，到 FCS 结束（若存在 FCS）。这说明 Preamble 不属于 Data Link Frame Size。

RFC 1242 同时将 Throughput 定义为 DUT 不丢弃任何 offered frame 时能够达到的最大转发速率。

### RFC 2544

https://www.rfc-editor.org/rfc/rfc2544.html

RFC 2544 要求在不同 Ethernet frame size 下测试吞吐量，并通过发送帧与接收帧数量判断吞吐极限。

## 7. 证据五：ITU-T G.984.2

ITU-T Recommendation：

https://www.itu.int/rec/T-REC-G.984.2/en

ITU-T G.984.2 定义 GPON 上行标准 nominal bit rate，其中包括 1244.16 Mbit/s。

对于本产品使用的 GPON 上行规格，标准值为 1244.16 Mbit/s。

### 单位换算说明

原讨论中曾出现 `1.24416 × 1024 ≈ 1274.24 Mbps` 的换算，该换算不应作为本问题判据。

网络速率使用十进制 SI 单位：

```text
1.24416 Gbit/s = 1244.16 Mbit/s
```

## 8. L1、L2 在本次测试中的含义

### 8.1 Ethernet L2

对于本次 Renix 报告，Frame Length = 84 Byte 对应 Ethernet Frame 长度口径。

L2 数据速率：

```text
L2 Rate = FPS × Frame Length × 8
```

### 8.2 Ethernet L1

Ethernet 在线路上连续发送 Frame 时，还存在 Preamble、SFD 和 IFG：

```text
| Preamble + SFD | Ethernet Frame | IFG |
|       8B       |      84B       | 12B |
```

因此每发送一个 84 Byte Frame，Ethernet 线路实际占用：

```text
84 + 8 + 12 = 104 Byte
```

L1 线路速率：

```text
L1 Rate = FPS × (Frame Length + 20) × 8
```

其中 20 Byte = 7 Byte Preamble + 1 Byte SFD + 12 Byte IFG。

## 9. 84 Byte 数据的计算证明

### 9.1 证明 1260 Mbps 是 L1 Rate

Renix 实测：

```text
FPS = 1,514,422
Frame Length = 84 Byte
```

计算：

```text
L1 Rate
= 1,514,422 × (84 + 20) × 8
= 1,514,422 × 104 × 8
= 1,259,999,104 bit/s
≈ 1260 Mbps
```

与 Renix 报告中的“转发速率（Mbps）= 1260”完全一致。

### 9.2 证明 1017.692 Mbps 是 L2 Rate

```text
L2 Rate
= 1,514,422 × 84 × 8
= 1,017,691,584 bit/s
≈ 1017.692 Mbps
```

与 Renix 报告中的“转发数据速率（Mbps）= 1017.692”完全一致。

因此可以确认本报告中的字段含义：

| Renix 字段 | 对应含义 |
|---|---|
| 转发速率（fps） | RX PPS |
| 转发速率（Mbps） | Ethernet L1 Rate |
| 转发数据速率（Mbps） | Ethernet L2/Data Rate |

## 10. 为什么 84 Byte 场景最容易出现“超过 1244”的表象

84 Byte 时：

```text
L1 / L2 = (84 + 20) / 84 = 104 / 84 ≈ 1.2381
```

因此 L1 比 L2 高约 23.8%。

而 1510 Byte 时：

```text
L1 / L2 = (1510 + 20) / 1510 ≈ 1.0132
```

只相差约 1.3%。

所以小包场景中，Preamble/SFD/IFG 占比高，L1 与 L2 的差异显著；大包场景中该差异快速缩小。

这与测试中“84 Byte 能看到 1260，大包在 1230~1245 左右进入丢包”的现象一致，不能单凭 84 Byte 的 L1 数字判断 PON 超规格。

## 11. BUG 定性

### 原判据

```text
Renix 转发速率 = 1260 Mbps
GPON 上行规格 = 1244.16 Mbit/s
1260 > 1244.16
⇒ PON 口超过规格
```

### 该判据的问题

1260 Mbps 是 Ethernet L1 Rate，而 1244.16 Mbit/s 是 GPON 侧 nominal bit rate。两者属于不同协议层、不同统计口径，不能直接比较。

同时，Renix 报告中 84 Byte 的 Ethernet L2/Data Rate 只有 1017.692 Mbps，且发包数等于收包数、丢包为 0。

### 最终结论

当前证据支持：

- 1260 Mbps 是 Renix Ethernet L1 线路速率显示；
- 1017.692 Mbps 是对应 Ethernet L2 数据速率；
- 两个数均可由 FPS 精确反算；
- 当前没有证据证明 GPON PON/GEM 实际承载突破 1244.16 Mbit/s；
- 当前没有由该现象导致的业务异常或丢包证据。

因此，BUG 1628980 以“PON 口流量超过规格”为核心的缺陷判据不成立。

## 12. 未解评审 Give Up 建议说辞

经重新核对信而泰 Renix RFC2544 原始报告，84 Byte、63% 场景中的 1260 Mbps 可以通过 `1,514,422 fps × (84+20) Byte × 8` 精确反算得到，说明该字段属于包含 Preamble/SFD 和 IFG 的 Ethernet L1 线路速率；同一行“转发数据速率”1017.692 Mbps 则可由 `1,514,422 × 84 × 8` 精确得到，对应 Ethernet L2/Data Rate。

原问题是把 Ethernet L1 的 1260 Mbps 直接与 GPON 1244.16 Mbit/s nominal bit rate 比较，属于不同层级、不同统计口径的跨层比较。现有数据不能证明 PON 口实际突破 GPON 上行规格，也没有对应业务异常或丢包。

因此本问题建议未解评审 Give Up。Give Up 不代表对所有内部带宽细节做了穷尽性证明，而是当前 BUG 的核心异常判据已经被实测数据和官方统计逻辑推翻，缺少继续按产品缺陷投入定位的依据。
